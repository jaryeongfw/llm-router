# 01. 문제 정의와 전제

## 문제

여러 LLM(벤더 프런티어 모델, 팀 GPU 서버의 자체 호스팅 모델 등)을 쓸 수 있을 때,
모든 요청을 가장 비싼 모델로 보내면 비용이 과하고, 가장 싼 모델로 보내면 품질이 무너진다.
요청마다 **충분히 잘하면서 가장 싼 모델**을 고르는 기준이 필요하다.

## 핵심 전제: 태스크 단위 고정 (session-pinned routing)

한 태스크는 하나의 모델 부류가 처음부터 끝까지 처리한다.
태스크 중간에 모델을 바꾸거나(per-turn routing), 한 태스크를 역할별로 여러 모델에 나누지 않는다.

### 고정을 택하는 이유

| 이유 | 설명 |
|---|---|
| 성능 일관성 | 중간에 모델이 바뀌면 말투, 코드 스타일, 판단 기준, 가정이 섞인다. 결과물의 품질 편차를 설명하기도 어려워진다. |
| 비용 효율 | 프롬프트 캐시(KV/prompt caching)는 모델별로 쌓인다. 중간 전환은 캐시를 버리고 누적 컨텍스트를 새 모델에 다시 읽힌다. 손실은 비대칭이다. 상향 전환은 회수되지 않고, 하향 전환은 1~2회 호출 안에 회수된다 (2610.19292, [06 문서 §2.1](06-literature-update-pi-plugin.md)). |
| 측정 용이성 | "이 태스크를 모델 X가 처리했고 결과는 Y"라는 라벨이 깨끗하게 남는다. 분할 실행은 결과 귀속이 모호하다. |
| 운영 단순성 | 오버헤드와 장애 지점이 줄어든다. 문헌에서도 세션 고정 선택이 매 턴 선택보다 부가 비용이 훨씬 작다고 보고된다 (VeriRouter, 2610.17431 — 검증 오버헤드 맥락). |

### 고정 방식이 감수하는 한계

- **쿼리만으로는 분리되지 않는 경우가 있다.** 비슷한 문장 뒤에 오타 하나가 숨어 있을 수도, 여러 모듈 리팩터링이 숨어 있을 수도 있다.
  태스크 설명만 보는 라우터에는 줄일 수 없는 오분류 하한(Bayes-error floor)이 있다는 지적이 있다 (SWE-Router, 2607.00053).
- 대응 방향 (고정 원칙은 유지):
  1. 모델을 돌리지 않고 얻는 **컨텍스트 신호**(저장소 검색 결과, 대상 파일 수, 코드 지표)를 쿼리 분석에 추가한다.
  2. 실패 시에는 중간 전환이 아니라 **상위 티어로 처음부터 재실행**한다. 이 재실행 기록이 라우터 보정 데이터가 된다. SWE-Router도 상향 시 처음부터 재시작한다. 이전 모델의 추론을 이어받으면 그 실수 쪽으로 편향되기 때문이다.
  3. (선택지) 싼 티어로 읽기 전용 탐색을 몇 턴 한 뒤 고정하는 "탐색 후 고정" ([06 문서 §5.4](06-literature-update-pi-plugin.md)).

## 목표

1. 쿼리를 받아 **필수 제약 판정 + 차원별 요구 수준**을 산출하는 분석 기준을 정의한다.
2. 모델별로 **같은 차원의 역량**을 측정하는 방법을 정의한다.
3. 둘을 결합해 "목표 품질을 만족하는 최소 비용 모델"을 고르는 결정 규칙을 정의한다.
4. 실행 결과로 기준과 임계값을 보정하는 피드백 경로를 갖춘다.

## 비목표

- 한 태스크 안에서 모델을 바꾸는 per-turn routing, 캐스케이드형 중간 전환
- 한 태스크를 역할별(계획/구현/리뷰)로 여러 모델에 분담시키는 멀티 에이전트 구성
- 서빙 계층의 요청 분산(같은 모델의 복제본 간 부하 분산, KV-aware routing 등)
- 대규모 학습형 라우터를 처음부터 만드는 것 (단순 기준선이 강하다는 문헌 결과가 있으므로 단순한 것부터 검증한다)

## 용어

| 용어 | 뜻 |
|---|---|
| 태스크 / 쿼리 | 사용자가 한 번에 맡기는 작업 단위. 라우팅 결정의 단위 |
| 모델 부류 (티어) | 비용·역량이 비슷한 모델 묶음. 예: 경량 / 표준 / 중량 |
| 필수 제약 | 위반하면 후보에서 제외되는 조건 (데이터 민감도, 부작용 등) |
| 선호 차원 | 성공 확률 추정에 쓰는 연속 점수 (난이도, 필요 역량 등) |
| 차원 | 쿼리 쪽 "요구 수준"과 모델 쪽 "역량"을 같은 축으로 표현하는 단위 |
