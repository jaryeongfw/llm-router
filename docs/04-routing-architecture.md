# 04. 라우팅 구조와 평가 계획 (초안)

## 1. 파이프라인

```
쿼리
 │
 ① 분석기 (규칙 + 소형 모델)
 │    → 태스크 유형, 필수 제약, 차원별 요구 수준, 난이도 분석 문장, 신뢰도
 │    → 컨텍스트 신호 수집 (저장소 검색, 파일 수, 토큰 추정, 코드 지표) — 모델 실행 없음
 │
 ② 필수 제약 필터
 │    → 후보 모델 부류 집합 축소
 │
 ③ 유사 과거 태스크 검색
 │    → 유형 + 난이도 분석 문장 + 차원 프로필이 비슷한 과거 태스크와 그 결과(성공/실패, 비용, 처리 모델)
 │
 ④ 성공 확률 추정
 │    → 후보 부류별 P(성공 | 쿼리 프로필, 모델 프로필, 유사 사례)
 │
 ⑤ 결정 규칙
 │    → argmin 비용  s.t.  P(성공) ≥ 목표 품질 τ
 │    → 해당 부류에 태스크 전체를 고정 배정
 │
 ⑥ 실행과 검증
 │    → 검증 실패 시: 상위 부류로 **처음부터** 재실행 (중간 전환 없음)
 │
 ⑦ 결과 기록 → ③④ 보정
```

## 2. 구성 요소

### 2.1 모델 프로필

모델 부류마다 **같은 차원의 역량**을 측정해 둔다.

```json
{
  "model_class": "standard",
  "models": ["provider/model-id"],
  "cost": { "input_per_mtok": 0.0, "output_per_mtok": 0.0, "unmetered": false },
  "latency_p50_s": 0.0,
  "capabilities_supported": ["tool_use", "long_context_128k"],
  "data_policy": "external_vendor",
  "ability": {
    "by_task_type": { "backend/code_modify": { "success_rate": 0.0, "variance": 0.0, "n": 0 } },
    "by_dimension": { "difficulty": 0.0, "multi_step_tools": 0.0, "code_correctness": 0.0 }
  },
  "instruction_form_sensitivity": "high"
}
```

- `by_task_type`: 태스크 유형별 성적표. Agent-as-a-Router에서 이것만 추가해도 효과가 컸다.
- `by_dimension`: IRT식 차원별 능력 추정치.
- `variance`: 반복 측정으로 얻은 성능 변동성 (DARS).
- `instruction_form_sensitivity`: 자유 서술 지시와 정형 지시 사이의 성능 차이 (NVIDIA tao 스킬 측정에서 작은 모델일수록 큼).
- 비용은 **실측 토큰 × 단가**로 기록한다. 단가가 같아도 모델별로 소비 토큰이 크게 다르다.

### 2.2 성공 확률 추정 — 단계별로 키운다

| 단계 | 방법 | 필요 데이터 | 근거 |
|---|---|---|---|
| v0 | **조회표**: 태스크 유형 × 난이도 구간 → 최소 부류 | 시드 측정 | LLMRouterBench (단순 기준선이 강함) |
| v1 | **유사 사례 검색**: 비슷한 과거 태스크의 부류별 성공률 | 경험 기억 | BoundaryRouter, VDAR-Router |
| v2 | **IRT형 모델**: P(성공) = σ(능력_m,k − 요구_q,k) 를 차원별로 결합 | 반복 측정 누적 | IRT-Router |

각 단계는 이전 단계를 기준선으로 삼아 **이길 때만** 채택한다.

### 2.3 결정 규칙

- 기본: `argmin 비용(부류)  s.t.  P(성공 | 부류) ≥ τ`
- `τ`는 운영 손잡이다 (Hybrid LLM). 예: 대화형 기본값, 배치 작업, 중요 태스크에서 다르게 둔다.
- 분석 신뢰도가 낮으면 한 부류 위로 올리거나 사용자에게 되묻는다.
- 재실행 비용을 포함한 **기대 비용**으로 비교할 수도 있다.
  `E[비용] = 비용(싼 부류) + (1 − P_싼) × 비용(상위 부류)` — 검증 가능성이 높을 때만 유효하다.

### 2.4 실패와 재실행

- 중간 전환은 하지 않는다. 검증 실패나 사용자 거절 시 **상위 부류로 처음부터** 다시 실행한다.
- 재실행이 일어난 태스크는 "하위 부류 실패, 상위 부류 성공" 라벨이 된다. 라우터 보정에 가장 값진 데이터다.
- 같은 태스크 재실행 횟수에 상한을 둔다.

### 2.5 결과 기록 스키마

```json
{
  "task_id": "...",
  "ts": "...",
  "analysis": { "...": "03 문서의 분석 출력" },
  "decision": { "model_class": "standard", "model": "provider/model-id", "tau": 0.8, "p_success": 0.83, "reason": "..." },
  "execution": { "tokens_in": 0, "tokens_out": 0, "cache_read": 0, "cost": 0.0, "duration_s": 0, "turns": 0 },
  "outcome": { "verified": true, "user_accepted": true, "rerun_from": null }
}
```

- 쿼리 원문을 그대로 남기지 않아도 되게 설계한다. 분석 결과와 난이도 분석 문장, 해시만으로 검색과 보정이 가능해야 한다. 기밀·개인정보가 로그에 쌓이는 것을 피하기 위함이다.

## 3. 평가 계획

### 3.1 시드 벤치마크 (오프라인)

1. 우리 업무의 태스크 유형별로 대표 케이스를 만든다 (유형당 10~20개). **합성 데이터 또는 비식별 데이터만** 쓴다.
2. 모든 후보 모델 부류로 실행한다. **케이스당 여러 번 반복**한다 (DARS: 단일 샘플 라벨은 불안정).
3. 성공 판정: 가능한 한 결정적 검증(테스트, 형식 검사)을 쓰고, 나머지는 고정된 판정 모델과 루브릭을 쓴다.
4. 결과로 모델 프로필(`by_task_type`, `by_dimension`, `variance`)과 v0 조회표를 만든다.

### 3.2 비교 기준선

| 기준선 | 의미 |
|---|---|
| 항상 최상위 부류 | 품질 상한, 비용 상한 |
| 항상 최하위 부류 | 비용 하한 |
| 무작위 (비용 맞춤) | 라우팅의 최소 기여 확인 |
| 규칙만 (v0) | 학습·검색 없는 단순 기준선 |
| 사후 오라클 | 각 태스크에서 성공한 최저 비용 부류. 상한 격차 측정 |

### 3.3 지표

- **성공률**, **총 비용**(실측 토큰 × 단가), **지연**
- **비용-품질 곡선**: `τ`를 바꿔 가며 운영점 비교
- **오라클 대비 후회(regret)**: 오라클 비용 대비 초과 비용, 오라클 성공 대비 손실
- **재실행률**: 하위 부류 배정 후 재실행된 비율 (과소 배정 지표)
- **과대 배정률**: 오라클이 더 싼 부류로 충분했던 비율
- 분석기 자체의 **비용·지연 비율**: 태스크 비용 대비 몇 %인지

### 3.4 Triage식 성립 조건 점검

라우팅이 이득이 되려면 최소한 다음을 만족해야 한다 (Triage의 조건을 일반화).
1. 싼 부류의 해당 유형 성공률이 **부류 간 비용비**보다 높아야 한다.
2. 분석 차원이 필요한 부류를 **유의미하게 구분**해야 한다. 구분력이 없는 차원은 제거한다.

## 4. 위험

| 위험 | 대응 |
|---|---|
| 쿼리만으로 범위를 오판 | 컨텍스트 신호 수집, 낮은 신뢰도면 보수적 배정 |
| 분석기 비용이 절감액을 잠식 | 규칙 우선, 소형 모델, 분석 비용 지표 감시 |
| 측정 라벨 노이즈 | 반복 측정, 변동성 기록, 판정 모델·루브릭 고정 |
| 모델 교체·추가 시 재측정 부담 | 모델 프로필을 대표 태스크 세트 성적으로 정의 (UniRoute) |
| 데이터 유출 | 데이터 민감도를 규칙 기반 필수 제약으로, 로그에 원문 미저장 |
| 차원 과다로 설명력 저하 | 구분력 없는 차원 제거, 5~6개 이내 유지 |
