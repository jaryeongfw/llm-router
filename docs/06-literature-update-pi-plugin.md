# 06. 문헌 보강 — pi 플러그인 구현 관점 (2026-11)

> 05 문서의 정독 우선순위 1~8 논문을 **본문 기준**으로 검토하고, 2026-11 기준 신규 문헌, pi 확장 API, 기존 pi 라우터 구현체를 추가 조사했다.
> 수치는 각 논문·문서가 보고한 값이며 재현하지 않았다. 신규 문헌은 따로 표시하지 않으면 **초록 기준**이다.
> 상세 목록은 [references.md](references.md) 참고.

## 0. 요약

1. **pi에는 라우터용 공식 API가 이미 있다.** `pi.registerVirtualModel()`의 `route(request, ctx)`가 요청마다 물리 모델을 고른다. `request.reason`(user / continuation / retry / direct)과 세션 분기에 저장되는 `state`로 세션 고정을 직접 구현할 수 있다. 05 문서의 Q8(어디에 붙일까)은 **pi virtual model**로 답이 정해진다.
2. **이미 비슷한 pi 라우터가 여러 개 공개되어 있다** (§4). 새로 만들 이유는 "측정 기반 성적표 + 보수적 필수 제약 + 재실행 라벨"이라는 차별점에 있다. 그대로 베끼지 말고 실패 사례를 참고한다.
3. **단순 조회표가 거의 모든 이득을 낸다.** 데이터셋/차원별 최고 모델을 고르는 조회표가 학습형 라우터와 비슷하거나 낫고 (LLMRouterBench의 Dataset Oracle, Agent-as-a-Router의 DimensionBest), 상용 라우터 6종 모두 "잘 고른 두 모델 사이 무작위 선택"을 이기지 못했다 (2610.02762). v0 조회표를 출발점으로 두는 방향이 더 강하게 뒷받침된다.
4. **비용은 캐시를 반영해 계산해야 한다.** 코딩 에이전트 입력 토큰의 98.6%가 캐시에서 나오고, 캐시를 무시한 정액 단가는 비용을 약 7배 과대평가한다 (TurnCost, 2610.15093). 티어 간 실제 비용 차이는 단가표보다 작다 (6.8배 → 3.2배, 2610.19292).
5. **세션 고정 원칙은 유지하되 근거를 고친다.** 캐시 손실은 방향에 따라 비대칭이다. 비싼 모델 → 싼 모델 전환은 1~2회 호출 안에 본전을 찾고, 싼 모델 → 비싼 모델 전환은 본전을 찾지 못한다 (2610.19292). 따라서 "중간 상향 전환 금지, 상향은 처음부터 재실행"은 맞다. 반면 "하향 1회 전환"은 비용상 허용할 여지가 있다.
6. **기존 문서에 정정할 내용이 있다.**
   - Triage(2604.07494)는 **실험 결과가 없는 제안 논문**이다. "중간급 모델만 깨끗한 코드에서 이득"이라는 관찰은 Borg et al.(2601.02200)의 **단일 파일 리팩터링** 결과를 인용한 것이다.
   - Agent-as-a-Router의 "+15.3%"는 LLM 라우터에 차원별 통계를 줬을 때의 향상이다. 같은 통계로 만든 조회표(DimensionBest)와의 차이는 47.74 대 47.50으로 미미하고, 성능/비용(Perf/$)은 조회표가 더 높다 (3.69 대 1.71).
   - SWE-Router는 상향할 때 **처음부터 재시작**한다. 중간 전환이 아니므로 이 프로젝트의 재실행 원칙과 호환된다.

## 1. 정독 결과 (본문)

### 1.1 IRT-Router (2506.01048)

| 확인 항목 | 내용 |
|---|---|
| 파라미터화 | MIRT: `P = σ(aᵢᵀθⱼ − bᵢ)`. 모델 능력 θ ∈ ℝ²⁵, 쿼리 변별도 a ∈ ℝ²⁵, 난이도 b는 **스칼라**. θ는 모델 **프로필 텍스트**(출시일, 개발사, 특징 설명)의 BERT 임베딩에서, a·b는 쿼리 임베딩에서 선형층으로 만든다. |
| 다차원 해석 | NIRT 변형은 25개 능력을 미리 정의하고(추론, 이해, 생성, 정보검색, …, 프로그래밍·알고리즘 등), 쿼리 군집(UMAP+HDBSCAN)마다 LLM이 관련 능력을 0/1로 표시한 관련도 벡터를 쓴다. 미관측 쿼리는 5-NN 평균으로 근사한다. |
| 결정 규칙 | `S = α·P̂ − β·C(M)`, α+β=1. 비용 C는 모델별 **고정값**(출력 단가 정규화)이고 자체 호스팅 모델은 0으로 둘 수 있다. |
| 워밍업 | 쿼리 임베딩을 k=5 최근접 학습 쿼리 평균과 섞는다: `e = (1−λ)e + λ·e_warm`. 분포 밖 데이터에서 λ=0.3~0.4가 유리했다. |
| 데이터 요구 | 학습 쿼리 전부를 **후보 20개 모델 모두로 실행**한 응답 행렬이 필요하다. |
| 주의점 | Top-1 라우팅 정확도는 2.7%로 낮다. 비슷한 성능의 모델이 많기 때문이라고 저자가 설명한다. |

**설계 반영**
- 차원별 요구 vs 능력을 비교하는 v2 모델로 쓸 수 있다. 다만 난이도가 스칼라 하나이고 능력 차원은 잠재 변수라서, 03 문서처럼 "차원마다 요구 수준 0~3"을 직접 대응시키는 구조와는 다르다. 우리 쪽에는 NIRT식 **명시적 관련도 벡터 × 차원별 능력**이 더 가깝다.
- Top-1 정확도가 낮다는 결과는 "모델 단위가 아니라 **티어 단위**로 라우팅한다"는 01 문서의 선택을 뒷받침한다.

### 1.2 Triage (2604.07494) — 정정

- **제안 논문이다.** 본문에 "This paper presents a new idea, not yet fully proven"이라고 밝힌다. SWE-bench Lite 300건 × 3티어 × 3회(총 2,700회 실행) 평가는 **설계만** 제시하고 결과는 없다.
- 비대칭 관찰의 출처: Borg et al. (2601.02200). 경쟁 프로그래밍 Python 파일 5,000개를 **단일 파일 리팩터링**한 실험에서 CodeHealth ≥ 9이면 중간 크기 LLM의 파손률이 상대 15~30% 줄었고, 에이전트형 Claude Code는 유의한 차이가 없었다.
- 쓸 만한 설계 요소:
  - 여러 파일을 건드리는 태스크는 **가장 건강도가 낮은 파일**을 기준으로 티어를 정한다.
  - 애매하면 대각선 위쪽(과대 지불)으로 둔다.
  - 기대 비용식: `r_L(c_L + f_L·c_H) + r_S(c_S + f_S·c_H) + (1 − r_L − r_S)·c_H`. 실패하면 **heavy로 재실행**한다.
  - 50건 파일럿의 go/no-go 조건: 비용 게이트(라이트 통과율 > c_L/c_H)와 신호 게이트(우위 확률 p̂ ≥ 0.56)를 **둘 다** 통과해야 한다.
  - 짝지은 설계(패치 크기로 난이도를 맞춘 쌍)로 코드 건강도와 난이도의 교란을 분리한다.
- 한계(저자 언급): 배포 시에는 대상 파일을 이슈 설명에서 추론해야 하고, 그 정확도가 상한이 된다. CodeHealth는 독점 지표다.

### 1.3 Arch-Router (2506.16655)

- 정책 표현: 라우트 정책 `cᵢ = (이름, 자연어 설명)` 집합 C, 매핑 `T: C → 모델`. 라우터는 쿼리와 **정책 설명 전체를 프롬프트로 받아** 정책 이름을 생성한다. 모델 교체는 T만 고치면 된다.
- 도메인-행위 2단 구조의 장점: 행위가 애매하면 도메인으로 물러설 수 있다.
- 성능: 단일 턴과 멀티 턴 전체에서 Claude Sonnet 3.7보다 약간 높았고(93.17% 대 92.79%), 지연은 28배 넘게 짧았다. 대형 모델을 압도한 것이 아니라 **비슷한 정확도를 훨씬 싸고 빠르게** 낸 결과다.
- 오류 패턴: **첫 턴에서 가장 많이 틀린다**(초기 의도가 모호할 때). 첫 턴을 맞히면 이후 턴은 안정적이다. 세션 시작 시 한 번 판단하는 구조에서는 이 첫 턴 정확도가 곧 성능이다.
- 한계(저자 언급): 정책 설명이 겹치면 임의로 고른다. 정책에 연결한 모델이 부적절하면 분류가 정확해도 결과가 나쁘다.
- **설계 반영**: 03 문서의 도메인·행위 목록은 **서로 겹치지 않게** 자연어 설명을 붙여 정의한다. 정책과 모델 매핑은 설정 파일로 분리한다.

### 1.4 LLMRouterBench (2601.07206)

- 기준선: Random Router(하한), **Best Single**(사후에 고른 최고 단일 모델), **Dataset Oracle**(데이터셋마다 최고 모델), Oracle(쿼리마다 최고 모델).
- 상위 라우터들이 Dataset Oracle 근처에 몰려 있다. 라우팅 이득의 상당 부분은 수학과 코드를 구분하는 수준의 **거친 도메인 구조**에서 나온다.
- Oracle과의 격차는 "정답을 내는 모델이 한두 개뿐인 쿼리"에서 그 모델을 고르지 못하는 **모델 회수 실패**에서 생긴다.
- 후보 수는 늘릴수록 효과가 줄어든다. 평균 정확도 상위 k개를 고르는 것이 무작위로 더 많이 넣는 것보다 낫다.
- 비용-성능 설정: Avengers-Pro(2508.12631, 임베딩 군집별 성능-효율 점수)가 파레토 전선을 거의 지배했다. 상용 OpenRouter auto는 Best Single 대비 −24.7%였다.
- 임베딩 백본(22.7M MiniLM 대 7B gte-Qwen2)의 영향은 미미했다.
- **설계 반영**: v0 조회표는 "태스크 유형별 최저 충분 티어"로 정의한다. 이는 Dataset Oracle의 티어판이다. 평가에서 Best Single과 Dataset Oracle을 반드시 기준선으로 둔다.

### 1.5 DARS (2606.06924)

- 관측 격자: 의미가 같은 **재작성 N개 × 확률적 디코딩 J회**. 기본 3×3=9회, 온도 0.7.
- 요약 통계: 기대 품질 μ_q, 기대 비용 μ_c, 품질 표준편차 σ_q.
- 효용: `U = μ_q − λ·μ_c − β·σ_q`, 기본 λ=0.05.
- 적응형 수집: 2×2로 시작해 애매한 쿼리만 3×3(최대 5×5)으로 늘린다. 쌍당 평균 7.75회로 9회 고정보다 13.9% 절감.
- 반복 관측은 **학습 라벨에만** 쓴다. 추론 시 라우터는 원본 쿼리만 본다.
- 한계(저자 언급): 단일 단계 라우팅만 다뤘다. 에이전트형 확장은 열린 문제다.
- **설계 반영**: 시드 벤치마크는 "케이스 × 티어 × 3회"를 기본으로 하고, 결과가 갈린 케이스만 늘린다. 재작성 변형은 우리 태스크 문장으로 2~3개 만든다.

### 1.6 Agent-as-a-Router (2606.22902) — 해석 보정

- 표 1 (Claude Sonnet 4.6이 라우터, 2,919 태스크):

  | 방식 | AvgPerf% | Perf/$ |
  |---|---|---|
  | Oracle | 57.00 | 8.20 |
  | **DimensionBest** (차원별 최고 모델 조회) | 47.50 | **3.69** |
  | Vanilla LLM 라우터 | 41.41 | 1.97 |
  | +차원 설명 | 41.18 | 1.81 |
  | +차원별 성적 통계 | 47.74 | 1.71 |

  - **차원 설명만 주면 효과가 없다**(41.18).
  - **성적표를 줘야 효과가 있다**(47.74).
  - 조회표 자체가 거의 같은 성능을 두 배 넘는 비용 효율로 낸다.
- 태스크 차원(CodeRouterBench) 10개: 코드 생성 / 알고리즘 설계 / 버그 수정 / 코드 완성 / 리팩터링 / 데이터 과학 / 다언어 / 코드 이해 / 테스트 생성 / 에이전트형 프로그래밍(분포 밖 시험용). 차원당 1,111건, MD5 기반 결정적 분할.
- ACRouter 구성: 메모리(태스크 임베딩 kNN, 상위 10개 이웃) + DimensionBest 사전 정보 + 휴리스틱 가중 투표 + 샌드박스 검증.
- **설계 반영**: 03 문서 3.1의 "행위" 목록 초안에 이 10개 분류를 대조한다. v1(유사 사례 검색)은 "조회표 + kNN 메모리" 조합이 문헌과 가장 가깝다.

### 1.7 VDAR-Router (2607.18098)

- 난이도 분석기: Qwen3.5-2B로 충분했고 Gemma4-31B와 비슷했다.
- 임베딩: Qwen3-Embedding-0.6B. 검색: FAISS top-k.
- 지연: 쿼리당 1.46초이고 대부분(1.43초)이 분석 문장 생성이다.
- 분석기 토큰 비용을 넣어도 기준선보다 좋았다.
- **설계 반영**: 세션당 한 번 판단하므로 1~2초 지연은 감당할 수 있다. 다만 분석 문장 생성은 **로컬 소형 모델**로 돌려야 데이터 민감도 제약과 충돌하지 않는다(§5.8).

### 1.8 SWE-Router (2607.00053) — 재해석

- 절차:
  1. 싼 모델 m1이 K턴(기본 K=3) 탐색한다.
  2. 값 헤드가 부분 궤적의 성공 확률을 추정한다.
  3. 임계값 이상이면 m1이 계속하고, 미만이면 **m2가 원래 문제 q에서 처음부터 재시작**한다.
- 재시작을 택한 이유(저자 언급): m2에게 m1의 추론을 이어받게 하면 **m1의 실수 쪽으로 편향**된다는 보고가 있었다. K턴 비용은 상향 시 총비용에 포함한다.
- 쿼리만 쓰는 기준선(임베딩+LR/kNN/XGB)의 AUROC는 SWE-bench Verified에서 0.53~0.57로 **무작위에 가깝다**.
- **설계 반영**: 이 방식은 "중간 전환"이 아니라 **탐색 후 고정(probe-then-pin)**이다. 이 프로젝트의 세션 고정, 처음부터 재실행 원칙과 충돌하지 않는다. 01 문서의 "그대로 쓰지 않는다"를 "선택지로 둔다"로 바꾼다(§5.4).

## 2. 신규 문헌

### 2.1 세션·캐시 경제학 (세션 고정 전제 재검토)

**Whose turn is it? Context-guided model routing for stateful agents (2610.19292)** — 본문 일부 확인
- 사용자 턴 경계에서 비용 인지 라우팅을 실험했다. 라우터에 **세션 이력을 주면** 같은 오프로딩 비율에서 통과율이 올랐고, 항상 비싼 모델을 쓰는 경우와 1점 이내였다.
- 긴 세션일수록 싼 모델의 비용 이점이 줄어든다(6.8배 → 3.2배). 비용은 토큰 단가보다 **실행 동학**(턴 수, 캐시)이 좌우한다.
- 닫힌 형태: 비싼 모델 e → 싼 모델 c로 하향 전환할 때 본전 회수 호출 수는 `k* = (p_c,in − p_e,cache) / (p_e,cache − p_c,cache)`이고 컨텍스트 길이와 무관하다. 논문의 가격에서 k* = 1.25였다.
- 상향 전환 비용은 `L·(p_e,in − p_c,cache)`이고 회수되지 않는다. 컨텍스트 75K 토큰에서 상향 한 번이 작업 하나 전체 비용과 맞먹었다.

**TurnCost (2610.15093)** — 본문 일부 확인
- 코딩 에이전트 궤적 600개를 분석했다.
  - 입력 토큰의 98.6%가 프리픽스 캐시에서 나온다.
  - **턴 수가 궤적 비용 분산의 84%**를 설명한다. 관측 크기는 4%만 설명한다.
- 비용 정산이 서로 다르다는 지적: AgentRouter는 출력 단가만, SWE-Router는 정액 추론 단가를, MTRouter는 정액 입출력 단가표를 써서 보고된 절감액끼리 비교하기 어렵다.

**SHADOWPREFILL (2611.13176)**: 서빙 계층 연구다. 실제 코딩 에이전트 트레이스(평균 컨텍스트 63K)에서 모델을 전환하면 프리픽스 적중률이 80~89%에서 44~65%로 떨어지고, 전환 호출 지연은 1.5~3.2배가 된다. 벤더 API를 쓰는 우리는 이 기법을 쓸 수 없지만, **전환 비용의 실측 근거**로 쓸 수 있다.

**MultiTurnRoute (2611.10848)**: 멀티턴 라우터 평가 플랫폼이다. 라우터 인터페이스에 "모델별 재사용 가능 프리픽스 길이 추정치"를 넣어 비용을 캐시 인지형으로 계산한다.

### 2.2 라우팅 회의론 (기준선 설계 근거)

**Dynamic LLM Routers are Often Misguided (2610.02762)**
- 상용 라우터 6종, 14개 설정 중 어느 것도 비용을 맞춘 "잘 고른 두 모델 무작위" 기준선을 이기지 못했다.
- 실패 패턴 4가지: 난이도 무시 / 길이 역전 / 출처 기반 의미 매칭 / 후보 구성 부적절.
- 표준 지표인 "실현 비용 기준 파레토 효율"이 앞의 세 패턴에 보상을 준다고 지적한다.
- 결론: 후보 구성을 잘하면 라우팅할 여지 자체가 작다.

**The Routing Plateau (2606.07587)**
- 21개 방법이 kNN을 포함해 좁은 범위로 수렴했다. 라우터는 주로 **모델별 전역 평균 성능**을 학습한다.
- 데이터와 인코더를 키워도 평균 +1.24pp에 그쳤다. 쿼리 밖의 입력(부분 궤적 등)이 필요하다고 결론짓는다.

**설계 반영**
- 기준선에 "**두 티어 무작위(비용 맞춤)**"를 추가한다.
- 오프라인 평가는 실현 비용 파레토만으로 판단하지 말고 난이도 구간별 배정 비율도 본다.

### 2.5 필수 제약·프라이버시

- **ComplianceGate (2606.31163)**: LLM 추론 **전에** 인코더 분류기(7ms)가 복잡도와 개인정보 포함 여부를 판정한다. 개인정보가 있으면 로컬 엔드포인트로 보내 데이터 상주 위반을 구조적으로 막는다. 03 문서의 "필수 제약은 규칙 우선" 원칙과 같다.
- **Sensitive-Topic Leakage Through LLM Routing Metadata (2610.09981)**: 콘텐츠 로그를 꺼도 **라우팅 결정 기록 자체가** 민감 주제를 드러낸다. RouteLLM 결정 20개로 의료 질문이 잦은 사용자를 AUC 0.71로 구분했다. 대화별 고정(stickiness)은 방어 수단으로 실패했다.
- **RouteBR (2611.07534)**: 모델은 경로를 **제안**만 하고, 실행 허가는 결정적 코드가 규칙으로 검사한다(fail-closed). 차단된 1순위 경로를 차순위로 대체하지 않는다.
- **설계 반영**
  - 데이터 민감도 판정은 **외부로 나가는 모든 호출보다 먼저** 로컬에서 한다. 외부 classifier 호출도 외부 호출에 포함된다(§5.8).
  - 라우팅 로그는 원문을 저장하지 않는 것에 더해, **로컬에만 보관하고 사용자 단위 집계를 외부로 내보내지 않는다**.
  - 민감도 제약에 걸린 태스크는 상위 티어가 외부 벤더뿐이라는 이유로 거기로 "대체"하지 않는다. 실패로 처리하고 사용자에게 알린다.

### 2.6 실행 전 난이도 신호 (Q7)

- **CABRA — Code Understanding is a Bottleneck for Coding Agents (2610.10610)**: SWE-bench Verified에서 **읽기·분석 도구 호출 수**가 편집 라인 수보다 정확도를 더 잘 예측했다. 에이전트의 난이도는 "고치기"보다 "이해하기"에 있다.
  → 범위 신호로 "편집 예상 파일 수"보다 **탐색이 필요한 양**(쿼리 심볼의 저장소 검색 매치 수, 호출 그래프 깊이)을 우선 측정할 근거다.
- **Borg et al. (2601.02200)**: CodeHealth와 AI 리팩터링 후 의미 보존 사이에 연관이 있다. 단일 파일, 경쟁 프로그래밍 코드 기준이다.

## 3. pi 플랫폼: 파이프라인 단계 → pi API

출처: pi-coding-agent 1.5.2 `docs/virtual-models.md`, `docs/extensions.md`, `docs/models.md`, `examples/extensions/jev-router.ts`.

| 파이프라인 단계 (04 문서) | pi 수단 | 비고 |
|---|---|---|
| 라우터 등록 | `pi.registerVirtualModel({ provider, id, route })` | `/model router/auto`로 선택한다. 하단 표시줄에 `auto → 실제 모델`이 나온다. |
| ① 분석 시점 | `route()`에서 `request.reason === "user"`이고 `request.state`가 없을 때 | `user`는 사용자의 모든 후속 메시지에서도 발생하므로 "새 태스크인가" 판단이 따로 필요하다(§5.5). |
| ① 소형 분류기 | `ctx.modelRegistry.classify()` / `findOfType("classifier", …)` | choice / bool / score 질문에 확률이 붙는다. llama.cpp 라우터의 채팅 모델도 classifier로 쓸 수 있어 **로컬 분류**가 가능하다. |
| ① 컨텍스트 신호 | `pi.exec()`(rg, git), `ctx.cwd` | 모델 실행 없이 저장소를 검색한다. |
| ② 필수 제약 | `route()` 안의 결정적 코드, `ctx.modelRegistry`의 모델 메타데이터(입력 유형, 컨텍스트 창) | 자격 증명이 없는 모델을 반환하면 오류가 난다. |
| ⑤ 고정 배정 | `route()`가 `state = { tier, model, … }`를 반환한다. 이후 `continuation`은 `request.previous`, `retry`는 `request.failed`를 반환한다. | state는 세션 트리를 따라가고 compaction 후에도 유지된다. `direct`(요약 등)에는 state가 없다. |
| 비용 정산 | 모델 `cost.input / output / cacheRead / cacheWrite / tiers`, 각 assistant 메시지의 `usage` | 캐시 인지 비용을 그대로 계산할 수 있다. `/session`에서 물리 모델별 비용을 볼 수 있다. |
| ⑥ 검증 신호 | `tool_result` / `tool_execution_end`(테스트·빌드 결과), `agent_end`, `agent_settled` | 결정적 검증은 bash 도구 결과에서 종료 코드를 읽는다. |
| ⑥ 처음부터 재실행 | `ctx.fork(entryId, { position: "before" })` 또는 `ctx.navigateTree()` + 상향 표시 | **파일 변경은 트리 이동으로 되돌려지지 않는다.** git 체크포인트가 필요하다(`examples/extensions/git-checkpoint.ts`). 구현 검증 필요. |
| ⑦ 결과 기록 | `pi.appendEntry(customType, data)`(세션 내), 로컬 파일/SQLite | 원문 대신 분석 결과와 해시를 남긴다. |
| 사용자 피드백 | `pi.registerCommand("router", …)` | 명시적 피드백, 수동 고정, 상태 조회. |

pi 문서가 명시한 운영 특성
- `continuation`에서 `previous`를, `retry`에서 `failed`를 반환해야 캐시와 thinking 서명이 유지된다.
- 라우터 안에서 classifier를 호출하면 첫 토큰 전에 지연이 추가된다.
- `route()`가 예외를 던지면 요청이 오류로 끝난다. **분류기 실패 시 기본 티어로 떨어지는 폴백**이 필수다.
- virtual model이 다른 virtual model로 라우팅할 수는 없다.

## 5. 설계 변경 제안 (01~05 문서 대비)

### 5.1 v0 = 티어판 Dataset Oracle
- 태스크 유형(도메인 × 행위)마다 "시드 벤치마크에서 τ를 만족한 가장 싼 티어"를 조회표로 만든다.
- 근거: Dataset Oracle(LLMRouterBench), DimensionBest(Agent-as-a-Router), Routing Plateau.
- LLM이 판단하는 라우터는 조회표를 이길 때만 들인다. LLM 라우터의 호출 비용이 비용 효율을 깎는다(Perf/$ 1.71 대 3.69).

### 5.2 후보 구성: 2티어로 시작
- 2610.02762와 LLMRouterBench 모두 후보 구성이 라우터 알고리즘보다 중요하다고 본다.
- **잘 고른 2티어**(예: 자체 호스팅 또는 경량 / 프런티어)로 시작한다. 중간 티어는 시드 측정에서 독립적 이득이 보일 때만 추가한다.

### 5.3 비용 모델: 캐시 인지 + 턴 수
- `비용(티어) = Σ턴 [비캐시 입력 × p_in + 캐시 읽기 × p_cache + 출력 × p_out]`
- 티어별 **예상 턴 수**와 **캐시 적중률**은 시드 측정에서 얻는다. 턴 수가 비용 분산의 84%를 설명한다.
- 04 문서의 기대 비용식은 Triage 식으로 확장한다. 재실행 비용은 상위 티어가 **q부터 다시 시작하는 비용**이다(컨텍스트 L이 작음).

### 5.4 세션 고정의 세 가지 모드 (선택지로 명시)

| 모드 | 동작 | 근거 | 위험 |
|---|---|---|---|
| A. 엄격 고정 (기본) | 세션 시작 시 한 번 결정. 실패하면 상위 티어로 q부터 재실행 | 01 문서 | 하한 오분류(쿼리만으로는 AUROC가 무작위에 가까움) |
| B. 하향 1회 | 강한 티어로 시작해 계획·첫 편집 후 싼 티어로 한 번 전환 | 2610.19292 (하향 k*≈1.25), jev-router | 스타일·가정 혼합(01 문서의 일관성 우려). 측정 라벨 귀속이 모호해짐 |
| C. 탐색 후 고정 | 싼 티어로 K≈3턴 탐색 후 계속 또는 상위 티어로 q부터 재시작 | SWE-Router | 탐색 턴 비용. 탐색 중 부작용 도구(쓰기, 배포)를 막아야 함 |

- 상향 중간 전환은 어떤 모드에서도 하지 않는다. 회수되지 않는 캐시 비용과 m1 실수에 대한 편향 때문이다.
- 모드 C는 **탐색 단계에서 읽기 전용 도구만 허용**(`pi.setActiveTools`)하면 부작용·가역성 제약과도 맞는다. 01 문서의 "모델 실행 없는 컨텍스트 신호"를 일반화한 형태로 볼 수 있다.

### 5.5 "태스크"의 경계
- pi의 `reason: "user"`는 같은 세션의 후속 지시에도 발생한다. "한 세션 = 한 태스크"라고 가정할 수 없다.
- 선택지:
  1. 새 세션(`/new`)에서만 재결정한다(단순).
  2. 목표 이탈을 감지해 재결정한다(@jangmanj/pi-router 방식).
- 재결정 결과가 **상향**이면 즉시 전환하지 말고 사용자에게 새 세션을 제안한다. 하향이면 그대로 전환해도 된다(2610.19292).
- 2610.19292에서 세션 이력을 본 라우터가 나았다. 재결정할 때는 첫 쿼리뿐 아니라 **지금까지의 세션 요약 신호**(변경 파일 수, 실패한 테스트 수)를 입력으로 쓴다.

### 5.6 측정 프로토콜
- 케이스 × 티어 × 3회. 결과가 갈린 케이스만 5회로 늘린다(DARS 적응형, Triage 3회 다수결).
- 차원 분류는 CodeRouterBench 10개 분류와 대조해 정한다.
- 기준선: 항상 상위 / 항상 하위 / **2티어 무작위(비용 맞춤)** / Best Single / Dataset Oracle(=v0) / 사후 오라클.
- 짝지은 분석: 난이도 대리 지표(예상 변경 규모)를 맞춘 쌍에서 신호(코드 건강도, 탐색량)의 구분력을 본다(Triage).
- go/no-go: 비용 게이트(하위 티어 통과율 > 비용비)와 신호 게이트(p̂ ≥ 0.56)를 모두 통과해야 한다.

### 5.7 보정과 피드백
- P(성공)은 등위 회귀로 보정한 뒤 τ와 비교한다(UCCI).
- 사용자 명시 피드백 없이 쓸 수 있는 암묵 라벨:
  - 상위 티어 재실행(가장 강한 실패 신호)
  - 사용자의 수동 모델 변경(`model_select` 이벤트)
  - 같은 요청 재시도(2602.02061)
  - 검증 도구의 종료 코드
  - 반복 도구 실패 루프
  - 세션 중도 포기
- 라벨이 30건 미만인 셀에서는 조회표 기본값을 유지한다. pi-smart-router 이슈에서 언급한 최소 표본 기준을 참고했으며, 실제 값은 측정 후 정한다.

### 5.8 데이터 민감도 처리 순서
```
쿼리 → [로컬 규칙 + 로컬 분류기: 민감도 판정]   ← 외부 호출 없음
        ├─ 민감 → 자체 호스팅 티어만 후보, 분석기도 로컬 모델만 사용
        └─ 비민감 → 외부 classifier 사용 가능
```
- jev-router 예제와 여러 선행 구현은 첫 사용자 메시지를 **외부 classifier**(TypeSafe, OpenAI Decisions 등)로 보낸다. 민감도 판정 전에 이렇게 하면 03 문서의 필수 제약을 분석 단계에서 이미 위반한다.
- 라우팅 결정 로그도 민감 정보 경로가 될 수 있으므로(2610.09981) 로컬에만 보관한다.
