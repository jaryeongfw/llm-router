# 03. 쿼리 분석 기준 (초안)

> 문헌([02-literature-map.md](02-literature-map.md))을 종합한 **설계 제안**이다.
> 근거 논문이 있는 항목은 표기했고, 표기 없는 항목은 이 프로젝트의 가정이다.

## 1. 구조: 필수 제약 → 선호 차원

```
쿼리 + 값싼 컨텍스트 신호
   │
   ├─ A. 필수 제약 (hard)    → 위반하는 모델 부류를 후보에서 제외
   │
   └─ B. 선호 차원 (soft)    → 남은 후보별 성공 확률 추정에 사용
                                 → "P(성공) ≥ 목표 품질"인 최소 비용 부류 선택
```

필수 제약과 선호 점수를 분리하는 구조는 제약 최적화 관점(MaxSAT, 2603.13612)과 맞고,
정책을 사람이 명시하는 방식(Arch-Router, 2506.16655)과도 맞는다.

## 2. A. 필수 제약

판정은 **보수적으로** 한다. 애매하면 제약이 걸린 것으로 본다.

| 제약 | 질문 | 판정 신호 | 위반 시 |
|---|---|---|---|
| **데이터 민감도** | 외부 벤더로 보내면 안 되는 정보가 포함되는가? | 사내 기밀 코드 경로, 개인정보·고객정보 패턴, 비밀정보 패턴, 사용자 명시 | 자체 호스팅 모델만 허용 |
| **부작용·가역성** | 실행 결과를 되돌릴 수 없는가? | 배포, DB 마이그레이션, 원격 쓰기(push, 외부 시스템 갱신), 삭제 | 하한 티어 이상만 허용 |
| **필요 능력 유무** | 모델이 기능적으로 지원하는가? | 도구 호출, 이미지 입력, 필요한 컨텍스트 길이, 구조화 출력 | 미지원 모델 제외 |
| **지연 상한** | 응답이 얼마나 빨라야 하는가? | 대화형 / 백그라운드, 사용자 명시 | 상한을 넘는 모델 제외 |
| **예산 상한** | 이 태스크에 쓸 수 있는 비용 한도는? | 태스크 유형별 정책, 사용자 명시 | 한도를 넘는 모델 제외 |

## 3. B. 선호 차원

각 차원은 쿼리 쪽 **요구 수준**(0~3)과 모델 쪽 **역량**을 같은 축으로 표현한다.
모델 쪽 역량은 [04-routing-architecture.md](04-routing-architecture.md)의 측정 계획으로 채운다.

### 3.1 태스크 유형 (분류 차원)

수준이 아니라 **범주**다. 모델 역량이 태스크 유형별로 다르므로, 다른 차원 점수를 해석하는 맥락이 된다.
근거: Arch-Router (도메인 × 행위), Agent-as-a-Router (태스크 차원별 통계의 효과).

- **도메인** (초안): 백엔드 / 프런트엔드 / 데이터·SQL / 인프라·운영 / 문서·보고서 / 일반 지식
- **행위** (초안): 설명·질의응답 / 코드 수정 / 신규 구현 / 리뷰 / 디버깅·원인 분석 / 설계·판단 / 문서 작성 / 데이터 분석·변환

### 3.2 난이도

| 수준 | 기준 |
|---|---|
| 0 | 단일 사실 확인, 정해진 변환 |
| 1 | 한두 단계 추론, 정해진 절차 따르기 |
| 2 | 여러 단계 추론, 여러 정보원 종합 |
| 3 | 트레이드오프 판단, 열린 설계, 정답이 하나가 아님 |

- 신호: 요구 동사(설명 / 수정 / 설계), 조건 수, 비교·판단 표현
- 산출: 분석기가 **난이도 분석 문장**을 함께 생성 (VDAR-Router 방식). 이 문장은 유사 사례 검색 키로도 쓴다.
- 근거: Hybrid LLM, VDAR-Router, IRT-Router

### 3.3 명세 완결성 (모호성)

| 수준 | 기준 |
|---|---|
| 0 | 목표 상태가 요청 문장만으로 확정됨 |
| 1 | 사소한 해석 여지 |
| 2 | 범위나 정책 해석이 필요함 |
| 3 | 목표 자체가 불명확, 사용자 확인 필요 |

- 수준 3은 라우팅 전에 **사용자에게 되묻기**를 우선 검토한다. 모호한 태스크를 비싼 모델에 보내도 모호함은 해소되지 않는다.

### 3.4 필요 역량 프로필 (다차원)

태스크가 요구하는 세부 역량. 각 0~3.
근거: BELLA (역량 행렬), IRT-Router (다차원 확장)

| 역량 | 예 |
|---|---|
| 긴 컨텍스트 이해 | 대형 파일, 여러 문서 종합 |
| 다단계 도구 사용 | 검색 → 읽기 → 수정 → 검증 루프 |
| 코드 생성 정확성 | 컴파일·테스트 통과 수준의 코드 |
| 지시·형식 준수 | 정해진 출력 형식, 체크리스트 준수 |
| 한국어 작문 품질 | 보고서, 문서, 공지 |
| 수리·논리 추론 | 계산, 알고리즘, 조건 분석 |

역량 목록은 모델 측정 결과를 보며 **줄여 나간다**. 서로 상관이 높은 역량은 합친다. 목표는 5~6개 이내.

### 3.5 범위·컨텍스트 규모

| 수준 | 기준 |
|---|---|
| 0 | 대상이 지정됨, 파일 1개 이하 |
| 1 | 대상 지정, 파일 2~5개 |
| 2 | 대상 탐색 필요, 또는 파일 6~20개 |
| 3 | 저장소 전반, 또는 예상 컨텍스트가 작은 모델의 안정 구간을 넘음 |

- **쿼리 텍스트만으로 추정하지 않는다.** 모델 실행 없는 컨텍스트 신호를 쓴다.
  - 쿼리에 언급된 심볼·경로로 저장소 검색 → 매치 파일 수
  - 대상 파일 크기와 토큰 추정
  - (코드 작업) 대상 코드의 건강도 지표: 복잡도, 결합도, 파일 길이 등 (Triage)
- 근거: Triage, SWE-Router가 지적한 쿼리 단독 판단의 한계

### 3.6 검증 가능성

| 수준 | 기준 |
|---|---|
| 0 | 결정적 검증 있음 (테스트, 빌드, 타입체크, 스키마 검사) |
| 1 | 부분 검증 가능 (일부 테스트, 실행해 보면 확인 가능) |
| 2 | 사람 검토로만 확인 가능 |
| 3 | 검증 불가 또는 결과가 늦게 드러남 (설계 판단, 운영 영향) |

- 검증 가능성이 높을수록(수준이 낮을수록) **싼 부류로 시도해도 실패 비용이 낮다.** 실패하면 검출되고 상위 부류로 처음부터 재실행하면 되기 때문이다.
- 근거: AutoMix, FrugalGPT의 캐스케이드 논리를 "재실행" 형태로 변형. Triage의 "같은 검증 게이트를 통과하는 최저 티어" 정의.

### 3.7 일관성 요구 (선택 차원)

같은 유형 태스크의 결과가 매번 비슷해야 하는가 (예: 정형 보고서, 코드 리뷰 형식).
- 일관성 요구가 높으면 **성능 변동성이 낮은 모델**을 선호한다.
- 근거: DARS (기대 품질과 함께 변동성을 요약)

## 4. 분석 출력 형식 (초안)

```json
{
  "task_type": { "domain": "backend", "action": "code_modify" },
  "hard_constraints": {
    "data_sensitivity": "internal_only",
    "irreversible_side_effects": false,
    "required_capabilities": ["tool_use"],
    "latency": "interactive",
    "budget_cap": null
  },
  "dimensions": {
    "difficulty": 2,
    "ambiguity": 1,
    "scope": 2,
    "verifiability": 0,
    "consistency": 1,
    "capabilities": {
      "long_context": 1,
      "multi_step_tools": 2,
      "code_correctness": 2,
      "instruction_following": 1,
      "korean_writing": 0,
      "reasoning": 1
    }
  },
  "difficulty_rationale": "두 서비스 계층에 걸친 수정이고 기존 예외 처리 규칙을 해석해야 함",
  "context_signals": { "matched_files": 7, "est_context_tokens": 18000 },
  "confidence": 0.7
}
```

- `confidence`가 낮으면 결정 규칙에서 한 단계 보수적으로 배정하거나 사용자에게 되묻는다.

## 5. 분석기 구현 원칙

1. **분석 비용은 태스크 비용보다 훨씬 작아야 한다.** 규칙과 패턴을 먼저 쓰고, 남은 판단만 소형 모델이 한다. Arch-Router는 1.5B 모델로 유형 분류가 충분하다고 보고했다.
2. **필수 제약은 규칙 우선**이다. 데이터 민감도와 부작용은 모델 판단에만 맡기지 않는다.
3. **분석 결과는 모두 기록**한다. 나중에 실제 결과와 대조해 차원 정의와 임계값을 보정한다.
