# 02. 문헌 지도 — 라우터는 무엇을 보고 판단하는가

> 모든 요약은 arXiv **초록 기준**이다. 수치는 각 논문이 보고한 값이며 재현하지 않았다.
> 2025~2026년 논문 상당수는 동료 평가 전 프리프린트다. 검토 수준은 [references.md](references.md) 참고.

## 1. 분류 틀

서베이 *Dynamic Model Routing and Cascading for Efficient LLM Inference* (2603.04445)는 라우팅 시스템을 세 축으로 나눈다.

| 축 | 질문 | 이 프로젝트의 선택 |
|---|---|---|
| **When** | 언제 결정하나 (생성 전 / 생성 후 / 매 턴) | **생성 전, 태스크당 1회** (세션 고정) |
| **What** | 무슨 정보를 쓰나 (쿼리, 컨텍스트, 과거 이력, 부분 응답) | 쿼리 + 모델 실행 없는 컨텍스트 신호 + 과거 유사 사례 |
| **How** | 어떻게 계산하나 (규칙, 분류기, 검색, RL, 최적화) | 규칙 + 소형 분석기 + 해석 가능한 성공 확률 추정 |

또 다른 서베이 *Doing More with Less* (2502.00409)는 라우팅을 **성능-비용 최적화 문제**로 정식화하고,
구현 방식을 유사도 기반 / 지도학습 / 강화학습 / 생성형으로 나눈다.
표준화된 실험 방법이 부족하고 비금전 비용(에너지, 지연)이 잘 다뤄지지 않는다는 점도 한계로 꼽는다.

## 2. 판단 신호별 문헌

### 2.1 태스크 유형 (도메인 × 행위)

**Arch-Router** (2506.16655)
- 쿼리를 사용자가 정의한 **도메인**(예: 여행)과 **행위 유형**(예: 이미지 편집) 선호에 매핑해 모델을 고른다.
- **1.5B 소형 모델**로 이 매핑을 학습했고, 인간 선호 일치도에서 대형 상용 모델보다 좋았다고 보고.
- 새 모델을 추가해도 라우터 재학습이나 구조 변경이 필요 없다. 정책(어떤 도메인·행위에 어떤 모델)은 사람이 정의한다.
- **시사점**: 태스크 유형 분류는 작은 모델로 충분하다. "분류는 학습, 배정 정책은 사람이 명시"하는 분리가 투명하고 운영하기 쉽다.

**Tryage** (2308.11601)
- 사용자 프롬프트를 실시간으로 적합한 LLM에 분배하는 초기 연구. 제목 수준만 확인했다.

### 2.2 난이도

**Hybrid LLM** (2404.14618)
- 쿼리 **난이도를 예측**해 소형 / 대형 모델에 배정한다. **목표 품질 수준을 실행 시점에 조절**해 품질과 비용을 맞바꿀 수 있다.
- 품질 저하 없이 대형 모델 호출을 **최대 40% 감소**시켰다고 보고.
- **시사점**: 결정 규칙에 "목표 품질" 손잡이를 두는 설계. 상황(대화형 / 배치, 중요도)에 따라 같은 라우터로 다른 운영점을 쓸 수 있다.

**VDAR-Router** (2607.18098)
- 쿼리마다 LLM이 **난이도 분석을 글로 생성**하고, 난이도 프로필이 비슷한 **과거 사례를 검색**해 후보 모델의 적합도를 추정한다. 학습이 필요 없다.
- 표면 의미나 임베딩 유사도만 쓰는 방법보다 비용 대비 성능이 좋았다고 보고.
- **시사점**: 임베딩 유사도만으로는 난이도를 놓친다. 분석 문장 자체를 검색 키로 쓰는 방식은 해석 가능하고 디버깅하기 쉽다.

### 2.3 난이도 × 모델 능력 (해석 가능한 측정 모델)

**IRT-Router** (2506.01048)
- 심리측정의 **문항반응이론(IRT)** 을 적용해 **쿼리 속성(난이도 등)과 모델 능력의 관계를 명시적으로 모델링**한다.
- 응답 성능을 예측하면서, 동시에 **모델 능력과 쿼리 난이도라는 해석 가능한 값**을 제공한다.
- 의미 유사도 기반 **온라인 워밍업**으로 콜드 스타트를 보완. 20개 LLM, 12개 데이터셋에서 평가.
- **시사점**: 이 프로젝트의 "쿼리 요구 수준과 모델 역량을 같은 차원으로" 구상에 가장 가깝다. 다차원 IRT로 확장하면 차원별 능력과 차원별 요구를 직접 비교할 수 있다.

### 2.4 필요 역량 프로필

**BELLA / Trust by Design: Skill Profiles** (2602.02386)
- 세 단계:
  1. 비평 모델로 LLM 출력을 분해해 태스크에 필요한 **세부 역량**을 뽑는다.
  2. 역량을 군집화해 **역량 행렬**을 만든다.
  3. 예산 제약 아래 다목적 최적화로 모델을 고른다.
- 추천 이유를 자연어로 제시한다. 금융 추론 도메인에 적용 사례를 논의(프레임워크 제안 성격).
- **시사점**: 집계 벤치마크 점수는 "이 태스크에 어떤 능력이 필요한지, 더 싼 모델로 충분한지"를 가린다. 차원을 "역량" 단위로 잘게 정의하는 근거.

### 2.5 차원별 과거 성적의 효과

**Agent-as-a-Router** (2606.22902)
- 코딩 태스크 라우팅에서 기존 라우터의 병목을 **정보 부족**으로 진단.
- 일반 LLM 라우터에 **태스크 차원별 성능 통계만 추가해도 15.3% 상대 향상**이 있었고, 같은 차원별 사전 정보로 만든 휴리스틱 라우터보다도 나았다고 보고.
  - (본문 확인) 다만 조회표(DimensionBest)와의 차이는 47.74 대 47.50으로 미미하고, Perf/$는 조회표가 더 높다(3.69 대 1.71). 차원 설명만 주면 효과가 없었다. → [06 문서 §1.6](06-literature-update-pi-plugin.md)
- 배포 중 실행 결과로 경험을 쌓는 루프(Context → Action → Feedback)를 제안. 오케스트레이터, 검증기, 메모리로 구성. 약 1만 건의 검증된 점수가 있는 CodeRouterBench(프런티어 LLM 8개)를 공개.
- **시사점**: 가장 싼 개선은 **"차원별 모델 성적표"를 라우터에 주는 것**이다. 모델 쪽 측정의 가치를 뒷받침한다.

### 2.6 실행 전 컨텍스트 신호 (코드 작업 특화)

**Triage** (2604.07494)
- ⚠️ (본문 확인) **실험 결과가 없는 제안 논문**이다. 아래 비대칭 관찰은 Borg et al. (2601.02200)의 단일 파일 리팩터링 결과를 인용한 것이다. → [06 문서 §1.2](06-literature-update-pi-plugin.md)
- 소프트웨어 엔지니어링 태스크를 **라이트 / 스탠다드 / 헤비** 세 티어(예: Haiku / Sonnet / Opus 급)에 배정한다.
- 라우팅 신호는 **미리 계산한 코드 건강도 하위 지표**(유지보수성 지표)와 태스크 메타데이터.
- 기준: 비싼 모델과 **같은 검증 게이트를 통과하는 가장 싼 티어**.
- 가설의 근거가 된 비대칭(Borg et al.): **중간급 모델은 깨끗한 코드에서 이득을 보지만 프런티어 모델은 그렇지 않다.**
- 비용 효율 라우팅이 성립하는 반증 가능한 조건 두 가지를 도출했다.
  1. 건강한 코드에서 라이트 티어 통과율이 티어 간 비용비를 넘어야 한다.
  2. 코드 건강도가 필요한 티어를 최소한의 효과 크기로 구분해야 한다.
- 평가 프로토콜(설계만 제시): SWE-bench Lite 300건, 휴리스틱 임계값 / 학습 분류기 / 완벽한 사후 오라클 비교.
- **시사점**: 쿼리 텍스트 대신 **대상 코드의 상태**가 강한 신호가 될 수 있다. "같은 검증을 통과하는 최저 티어"라는 정의는 성공 라벨로 그대로 쓸 수 있다.

**SWE-Router** (2607.00053) — 세션 고정의 한계를 보여주는 대조 사례
- 태스크 설명만 보는 라우터에는 **정보 이론적 오분류 하한**이 있다고 지적.
- 싼 모델을 몇 턴 탐색시킨 뒤 부분 궤적을 보고 계속할지 비싼 모델로 올릴지 결정한다. 부분 궤적을 조건으로 쓰면 라우팅이 나빠지지 않는다는 베이즈 최적성 정리를 제시.
- (본문 확인) 상향 시 강한 모델은 **원래 문제에서 처음부터 재시작**한다(K=3 탐색 후 판정). 중간 전환이 아니라 "탐색 후 고정"이다.
- **시사점**: 세션 고정, 처음부터 재실행 원칙과 호환되므로 선택지로 둔다([06 문서 §5.4](06-literature-update-pi-plugin.md) 모드 C). "탐색 정보"를 **모델 실행 없이** 얻는 방법(저장소 검색, 정적 지표)도 계속 찾는다.

### 2.7 유사 사례 경험 기억 (콜드 스타트)

**BoundaryRouter** (2605.07180)
- 경량 LLM 직접 응답과 전체 에이전트 실행 중 무엇을 쓸지 결정한다.
- 공유 시드 세트에서 **양쪽을 모두 실행해 경험 기억**을 만들고, 추론 시 유사 사례를 검색하고 루브릭으로 추론해 판단한다. 학습 불필요.
- 에이전트 대비 추론 시간 60.6% 감소, 직접 응답 대비 성능 28.6% 향상을 보고. 의역 / 도메인 외 설정도 포함한 RouteBench 제시.
- **시사점**: 초기에는 대표 태스크 시드 세트를 모든 후보 모델로 돌려 경험 기억을 만드는 것이 현실적인 출발점이다.

### 2.8 제약 조건 기반 해석

**LLM Routing as Reasoning: A MaxSAT View** (2603.13612)
- 자연어 선호를 모델 속성에 대한 **필수 / 선호 제약**으로 바꿔 가중 MaxSAT/MaxSMT 문제로 라우팅을 해석한다. 25개 모델 벤치에서 분석.
- **시사점**: 이 프로젝트의 "필수 제약 필터 → 선호 점수 최적화" 2단 구조가 정식 최적화 관점과 맞는다.

### 2.9 학습형 라우터와 모델 표현

**RouteLLM** (2406.18665)
- 강한 모델 / 약한 모델 중 선택을 **인간 선호 데이터**와 데이터 증강으로 학습. 일부 설정에서 품질 손실 없이 비용을 2배 넘게 절감.
- 학습 후 강·약 모델을 바꿔도 성능이 상당 부분 유지(전이)된다.

**UniRoute — Universal Model Routing** (2502.08773)
- 각 LLM을 **대표 프롬프트 세트에 대한 예측 결과 벡터**로 표현해, 학습 때 보지 못한 새 모델도 라우팅 후보로 편입. 30개 이상 미관측 LLM에서 평가.
- **시사점**: 모델 쪽 프로필을 "대표 태스크 세트 성적"으로 정의하면 모델 교체·추가가 쉽다.

**RouteFM** (2609.37362)
- 라우팅을 파운데이션 모델 관점으로 접근. 익명 후보 모델의 행동 맥락만으로 능력을 추론하도록 에피소드 사전학습. 후보당 관측 8개만으로 기준선보다 좋았다고 보고.

그 외 참고: RouterDC (2409.19886, 이중 대조학습), GraphRouter (2410.03834, 그래프 기반), EmbedLLM (2410.02223, 모델 임베딩), MixLLM (2502.18482), Router-R1 (2506.09033, 다회 라우팅 + RL).

### 2.10 캐스케이드 (참고: 세션 고정과 충돌)

**FrugalGPT** (2305.05176)
- 비용 절감 전략을 프롬프트 적응 / LLM 근사 / **LLM 캐스케이드** 세 가지로 정리.
- 캐스케이드로 최고 단일 모델 성능을 맞추면서 최대 98% 비용 절감을 보고.

**AutoMix** (2310.12963)
- 소형 모델 출력의 **자기 검증**으로 대략적 정답 여부를 추정하고, POMDP 라우터로 더 큰 모델로 보낼지 결정. 비슷한 성능에서 50% 넘게 비용 절감을 보고.

**이 프로젝트에서의 해석**: 중간 전환은 하지 않는다. 대신 "검증 실패 시 상위 티어로 **처음부터** 재실행"하는 변형으로만 쓴다. 검증 가능성이 높은 태스크일수록 싼 티어로 시도해도 되는 근거가 된다.

### 2.11 매 턴 라우팅 (대조군)

**RIVET — Response-Informed Value Estimation** (2610.23239), **MTRouter** (2604.23530)
- 멀티턴에서 턴마다 모델을 고르는 방식. 학습 때만 실제 응답을 보는 가치 추정기를 함께 학습시켜 배포 시 사전 정보만으로 라우팅한다. MINT 벤치에서 총 호출 비용 74.7% 절감을 보고.
- **시사점**: 로그된 궤적의 응답 정보를 **학습 신호로만** 쓰는 아이디어는 세션 고정에도 쓸 수 있다. 실행 결과를 사후 라벨로 쓰되, 배포 시에는 실행 전 정보만 쓴다.

## 3. 현실 점검 문헌

**LLMRouterBench** (2601.07206)
- 40만 건 이상, 21개 데이터셋, 33개 모델, 라우팅 기준선 10개로 분야를 재평가.
- 모델 간 상호보완성(라우팅의 전제)은 확인했지만, **많은 라우팅 방법이 통일 평가에서 비슷했고, 상용 라우터를 포함한 최근 방법 일부는 단순 기준선을 안정적으로 이기지 못했다.**
- 오라클과의 격차는 주로 **적합한 모델을 떠올리지 못하는 실패**에서 나온다.
- 임베딩 백본의 영향은 제한적이고, **앙상블을 크게 하기보다 후보 모델을 신중히 고르는 것**이 낫다.

**DARS — From Sampled Outcomes to Capability Distributions** (2606.06924)
- 쿼리-모델 쌍마다 **응답 한 번으로 라벨을 만들면 불안정**하다. 의미가 같은 쿼리 변형이나 디코딩 반복에 따라 점수와 선호 모델이 바뀐다.
- 반복 관측으로 **기대 품질, 기대 비용, 성능 변동성**을 요약해 위험을 고려한 지도 신호를 만든다. 라우터 구조는 바꾸지 않는다.
- **시사점**: 모델 측정은 반복 실행 분포로 해야 한다. 변동성 자체가 라우팅 차원이 될 수 있다(일관성이 중요한 태스크에서는 분산이 낮은 모델 선호).

**RouterBench** (2403.12031), **RouterEval** (2503.10657): 라우팅 평가용 벤치마크.

## 4. 인접 참고: NVIDIA Agent Skills의 평가 방식

NVIDIA Agent Skills 카탈로그(github.com/NVIDIA/skills)는 라우팅 연구는 아니지만, 모델 쪽 측정 설계에 참고할 점이 있다.

- **평가 차원 5개**: Security / Correctness / Discoverability / Effectiveness(목표 달성 50% + 절차 준수 50%) / Efficiency(도구 호출 생산성 50% + 토큰 50%).
- 판정: 차원별 50% 이상 PASS, 40~50% NEUTRAL, 40% 미만 FAIL. 부정 케이스(쓰지 말아야 할 때 쓰지 않는지) 포함.
- `tao-token-efficient-execution` 스킬의 측정 (스킬 문서 기준):
  - 실행 모델 크기별 하한: 프런티어 무결점 / ~400B MoE 거의 무결점 / ~35B MoE 작업에 따라 다름 / ~30B dense 하한 미달.
  - **원본 지시 그대로는 측정한 작은 모델 중 어느 것도 정직하게 완료하지 못했고**, 단계별로 정형화한 지시에서만 실행 가능했다.
  - 시사점: 모델 역량은 **지시 형태**(자유 서술 vs 정형화)에 따라 크게 달라진다. 모델 측정 시 이 변수를 통제하거나 기록해야 한다.
