# 08. 라우팅 판단 평가 (2026-11-12)

> 원자료: [`bench/results/`](../bench/results/README.md) (1차 = `1-baseline-*`, 재평가 = `2-*` ~ `4-*`).
> 재현: `node scripts/eval-routing.ts --analyzer <policy|모델> [--rescore bench/results/raw/<파일>]` (원시 기록은 로컬 전용, git 제외).

## 1. 무엇을 쟀나

경로는 실제 런타임과 같다: 1단 규칙 → 2단 분석기(local 모델, pi CLI 경유) → `decide()`.

- **시드 케이스 30건 × 표현 3가지(원문, 변형 2개) = 90건**
  - 분석 결과를 사람 라벨과 비교한다.
  - 분석으로 나온 결정을, 사람 라벨에 같은 결정 규칙을 적용한 결정(이하 "라벨 결정")과 비교한다.
- **분석기 정답 세트 44건**: 행위, 난이도, 모호성, 민감도 판정을 본다.
- **잰 것은 분석기 충실도다. 라우팅의 품질이 아니다.**
  - 조회표가 아직 가설값(prior)이고, 라벨도 한 사람이 붙였다.
  - "라벨 결정"이 최적이라는 근거는 없다. 고른 티어가 실제로 성공하는지는 결과 기준 평가(§5)에서 따로 본다.
- 외부 벤더 호출은 없다(로컬 판단 모델만 사용).

## 3. 해석

### 3.1 분류는 정확하고, 결정은 난이도 ±1에 흔들린다
- 티어 불일치 36건의 원인:

  | 원인 | 건수 |
  |---|---|
  | 난이도 차이 | 20 |
  | 난이도 차이 + `verifiable_down` 경계 | 10 |
  | `verifiable_down` 경계만 | 4 |
  | 행위 오분류 | 2 |

- 분석기의 난이도는 거의 항상 라벨과 1 이내다(98.9%). 하지만 조회표가 계단 함수라서 1 차이가 그대로 티어 차이가 된다.
- `verifiable_down`(검증 가능하고 난이도 ≤ 1이면 한 단계 아래)은 난이도 1과 2 사이의 절벽이다. 난이도 1↔2 혼동(17건)이 여기서 티어 두 단계 차이로 커진다.
- 분석기는 **중간으로 몰린다.**
  - 라벨 3 → 2가 12건 중 8건, 라벨 0 → 1이 12건 중 7건이다.
  - 그 결과 standard가 8건에서 14건으로 늘고, heavy는 6건에서 3건, local은 13건에서 7건으로 줄었다.
- 표현 변형 간 흔들림도 같은 원인이다. 흔들린 11건 모두 난이도나 `verifiable_down` 경계에서 갈렸다.
- LLMRouterBench와 Routing Plateau(06 §1.4, §2.2)가 말한 "거친 도메인 구조가 이득의 대부분"과 맞는 결과다. 분석기에서 믿을 만한 신호는 **행위**이고, 난이도는 거친 신호다.

### 3.2 로컬 모델 서버가 비밀정보 요청을 거부한다 (새 사실)
- local 모델는 AWS 키나 `sk-` 키 형식이 든 요청에 **403**을 즉시 돌려준다. 전화번호 형식은 통과했다.
- pi가 403을 재시도해서 평가에서는 약 30초 뒤 실패했다. 이어서 대체 모델(다른 로컬 모델 서버)은 503(네트워크 차단)으로 실패했다.
- 결과적으로 secret이 든 태스크는 **배정할 local 티어가 없다.** 지금 규칙(secret → local)은 실제로 동작하지 않는다.

### 3.3 지연이 목표(3초)를 크게 넘는다
- 동시 1개: p50 6.9초(CLI 시작 1~1.9초 포함)
- 동시 3개: p50 9.1초, p95 19초. 30초 시간 초과가 2건 났다.
- 서버가 요청을 직렬로 처리하는 것으로 보인다. 분석기와 local 티어를 같은 모델로 쓰면 서로 지연을 키운다(07 §13 S8).

## 6. 조치 반영과 재평가 (같은 날)

### 6.1 반영한 결정 (사용자, 2026-11-12)

| 제안 | 결정 | 반영 |
|---|---|---|
| A1 | 구간으로 거칠게 | 조회표 키를 (행위, easy/hard)로 바꿈. 세부 난이도는 추론 강도에만 쓰고, 구간 상단이면 +1 |
| A2 | 좁히기 | `verifiable_down`은 **난이도 0일 때만**. 아래 §6.3 비교로 정함 |
| A3 | 비밀정보는 opus로 시도, 실패하면 차단 → **§7에서 재설계: 모든 모델 호출에서 가림** | 07 §6.5 |
| A4~A6 | Claude 경량 모델로 분석기 검토 | external_ok 요청은 haiku-5-5(thinking off), internal_only 요청은 local 모델. 앵커 예시 8개 추가 |

A3을 반영하면서 두 가지 문제를 찾아 고쳤다.
- 분석기가 가린 자리를 보고 "민감 의심"을 내면 로컬 전용 + 비밀정보가 되어 **비밀정보 사례 7건이 모두 차단**되었다. 이미 가린 요청에서는 2단 의심을 반영하지 않도록 고쳤다(`src/analyze.ts`).
- 접속 문자열 `user:pw@host`가 이메일 규칙에도 걸렸다. secret 규칙을 먼저 적용하고, 나머지 규칙은 가린 텍스트에 적용하도록 고쳤다(`src/stage1.ts`).
- 비밀번호 대입 규칙이 `secret: true`, `token = getToken()` 같은 **코드 식별자**에도 걸렸다. 코드를 붙여 넣은 요청이 opus로 강제 배정될 수 있었다.
  - 값이 따옴표 리터럴이거나, 영문·숫자가 섞인 8자 이상 값일 때만 잡도록 좁혔다.
  - 정답 세트에 코드 조각 오탐 유도 2건(neg-09, neg-10)과 따옴표 리터럴 양성 1건(sec-08)을 추가했다(47건).
  - secret 재현율과 정밀도는 모두 100%다.

### 6.2 결과 비교 (시드 케이스 90건 + 정답 세트 44건, 모두 현재 규칙으로 채점)

| | 1차 (v1 규칙) | A: v2 규칙만 | B: local 모델 + 앵커 | C: haiku 정책 + 앵커 |
|---|---|---|---|---|
| 행위 일치 (케이스) | 97.8% | 97.8% | 95.6% | 97.8% |
| 난이도 구간 불일치 | — | 20.0% | **14.4%** | 20.0% |
| **티어 일치** | 60.0% | 75.6% | **80.0%** | 74.4% |
| (티어, 추론 강도) 일치 | 55.6% | 61.1% | **66.7%** | 54.4% |
| 과소 / 과대 배정 | 16.7% / 23.3% | 10.0% / 14.4% | 11.1% / 8.9% | 14.4% / 11.1% |
| **세 표현 모두 같은 티어** | 63.3% | 63.3% | 73.3% | **83.3%** |
| 정답 세트 행위 일치 | 83.3% | 83.3% | 83.7% | 86.4% |
| 민감도 재현율 / 정밀도 (1단+2단) | 100% / 94.4% | 100% / 90.9% | 100% / 90.9% | 100% / 83.3% |
| 비밀정보 → heavy, 개인정보·기밀 → local | — | — | 7/7, 10/10 | 7/7, 10/10 |

| 3초 이내 | 0% | 0% | 0% | **89.6%** |

정답 세트의 비밀정보 사례는 정책 변경으로 라벨이 바뀌었다(internal_only → external_ok + secret_present). 그래서 민감도 행의 분모가 17에서 10으로 줄었다.

해석:
- **결정 규칙 변경(A1·A2)만으로 티어 일치가 60%에서 75.6%로 올랐다.** 같은 분석 결과를 다시 채점한 것이라 분석기 차이가 섞이지 않았다.
- 앵커 예시는 local 모델의 난이도 구간 오류를 20%에서 14.4%로 줄였다. 그 결과 티어 일치가 80%가 됐다.
- haiku는 라벨과의 일치가 local 모델보다 약간 낮다(74.4%). 대신 **표현이 달라도 결정이 더 안정적이고(83.3%), 3.5배 빠르다.**
  - 라벨 일치는 한 사람이 붙인 라벨 기준이다. 안정성은 라벨과 무관한 지표라 더 믿을 만하다.
- 남은 불일치의 주원인은 난이도 구간 경계(1↔2)다(07 §13 S11). 어느 쪽이 맞는지는 결과 기준 평가로만 알 수 있다.

### 6.3 A2 조건 비교 (C의 분석 결과로 다시 채점)

| verifiable_down 조건 | 티어 일치 | 세 표현 같은 티어 | 과소 배정 |
|---|---|---|---|
| 난이도 0, 또는 신뢰도 ≥ 0.9이면서 난이도 ≤ 1 | 62.2% | 76.7% | 12.2% |
| **난이도 0만 (채택)** | **74.4%** | **83.3%** | 14.4% |
| 난이도 ≤ 1 전부 | 65.6% | 76.7% | 12.2% |

신뢰도 조건은 새 경계를 만들었다. 분석기 신뢰도가 표현에 따라 0.85와 0.9 사이를 오갔기 때문이다.

### 6.4 분석기 권고

- **external_ok 요청은 haiku-5-5(현재 정책)를 유지한다.**
  - 3초 목표를 맞추는 유일한 선택지다. 안정성도 가장 높다.
  - 분석 비용은 요청당 약 $0.0005다. 입력 약 3.5K 토큰, 출력 약 300 토큰.
- internal_only 요청은 local 모델를 쓴다. 지연(p50 7초)은 남은 문제다(07 §13 S8).
- 플러그인에서는 CLI 시작 시간(1~1.9초)이 빠진다. 실제 지연은 표보다 짧다.

## 7. 비밀정보: 모든 모델 호출에서 가림 (A3 재설계)

### 7.1 왜 바꿨나
- A3(비밀정보는 opus로 원문 전송)에는 두 가지 문제가 있었다.
  - 로컬 모델 서버가 비밀정보를 403으로 거부했다. 그런데 원문을 외부 모델로 보내면, 로컬에서도 막는 정보를 더 바깥으로 내보내게 된다.
  - 가림이 사용자 프롬프트에만 적용됐다. 에이전트가 `.env`를 읽으면 도구 결과로 비밀 값이 그대로 나갔다. local 티어는 그 순간 403으로 멈췄다.
- 그래서 라우터 플러그인이 **모델로 나가는 모든 메시지**에서 비밀 값을 가리고, 도구 실행 직전에 되돌린다(07 §6.5). `secret_policy` 기본값은 `mask`다. 티어 강제 배정은 없다.

### 7.2 종단 간 검증 (실제 pi 실행, `node scripts/e2e-secret-guard.ts`)
- 설정:
  - 임시 저장소에 가짜 AWS 키와 `sk-` 토큰이 든 `.env`를 둔다.
  - 검사용 확장이 `before_provider_request`에서 **공급자 요청 본문**에 비밀 값이 있는지 매번 센다.

| 모델 | 시나리오 | 공급자 요청 / 비밀 값 포함 | 작업 확인 |
|---|---|---|---|
| haiku-5-5 | S1 `.env` 읽고 변수 이름 나열 | 2 / 0 | 통과 |
| haiku-5-5 | S2 토큰으로 `node check.mjs <값>` 실행 | 2 / 0 | `TOKEN_OK` |
| haiku-5-5 | S2b 값을 명령에 직접 적게 함 | 3 / 0 | 자리표시가 복원되어 `TOKEN_OK` |
| haiku-5-5 | S3 LOG_LEVEL만 수정 | 3 / 0 | 비밀 값 줄 보존 |
| local 모델 | S1 / S2 / S2b / S3 | 2 / 0, 4 / 0, 3 / 0, 4 / 0 | 모두 통과. **작업 중 403 없음** |
| haiku-5-5 (가림 없음, 대조) | S1 | 2 / **1** | 검사 장치가 유출을 잡음 |

- 처음에는 haiku가 자리표시를 "가려져서 쓸 수 없는 값"으로 보고 명령 실행을 거부했다. local 모델는 그대로 썼다.
- 시스템 프롬프트 지침(`before_agent_start`)을 넣은 뒤 두 모델 모두 자리표시를 명령에 넣었고, 실행 직전에 실제 값으로 복원됐다.

### 7.3 남은 한계
- 규칙이 모르는 비밀 형식은 그대로 나간다(07 §13 S13).
- 시스템 프롬프트는 가리지 않는다(S12).
- 값의 내용을 직접 봐야 하는 작업은 할 수 없다.

## 8. 쿼리별 분배와 판단 모델 자동 선택 (런타임 검증)

변경(사용자 결정, 2026-11-12):
- 결정 단위를 세션에서 **사용자 쿼리**로 바꿨다. 쿼리 안의 도구 루프는 그 쿼리의 결정을 유지한다.
- 판단 모델 기본값을 **local 모델**로 바꿨다. 특정 모델명을 쓰지 않고 사용자 설정 `local_models`를 따른다.
- local이 없으면 **Claude 판단 모델을 자동 선택**한다.

### 8.1 한 세션에 4개 쿼리 (`node scripts/e2e-routing.ts`, pi RPC, router/auto:medium)

| # | 쿼리 | 결정 | 판단 모델 (지연) | 실제 응답 모델 (호출 수) |
|---|---|---|---|---|
| 1 | TCP·UDP 차이 한 문장 | local · off (explain/easy) | local 모델 (6.3초) | local 모델 (1) |
| 2 | bash로 파일 목록 보고 설명 | local · off (explain/easy) | Claude haiku (14.2초, local 시간 초과 후 대체) | local 모델 (3, 도구 루프 유지) |
| 3 | 모놀리스 분리 vs 이벤트 기반 권고 | heavy · opus-5-5 · xhigh (design/hard) | local 모델 (9.1초) | opus-5-5:xhigh (1) |
| 4 | 개인정보 포함 안내 문구 | local · off (로컬 전용) | local 모델 (6.9초) | local 모델 (1) |

- 쿼리마다 결정이 새로 내려졌다(결정 로그 4건).
- 각 쿼리의 모든 응답이 그 쿼리의 결정 모델·추론 강도와 같았다.
- 처음 실행에서는 쿼리 2~4의 2단이 실패했다. 측정한 local 모델이 **추론형**이라 사고 과정이 출력 상한(800토큰)을 다 써서 본문이 비었다. 그래서 상한을 `analyzer.max_tokens`(기본 4096)로 올리고, 본문이 빈 응답은 실패로 보고 다음 판단 모델로 넘기도록 고쳤다.

### 8.2 local 모델이 없는 환경 (`--no-local`)

|---|---|---|---|
| 1 | 쉬운 설명 | light · haiku-5-5 · off | Claude haiku 자동 선택 (1.9초) |

### 8.3 세션 고정 옵션 (`--scope session`)
- 결정 기록은 1건이었고, 네 쿼리 모두 첫 결정(local)을 유지했다.
- 여기서 안전 문제를 발견했다. 첫 결정이 외부 모델이면 이후 개인정보 쿼리도 그 외부 모델로 간다. 그래서 고정 중에도 1단 규칙을 쿼리마다 검사하도록 고쳤다. 로컬 전용 데이터인데 고정 모델이 local이 아니면 그 쿼리는 다시 결정한다(`test/runtime.test.ts`).

### 8.4 지연
- local 판단 모델은 쿼리마다 6~9초가 걸렸고, 시간 초과 시 14초까지 늘었다. Claude haiku는 1.5~2초였다.
- 쿼리별 분배에서는 이 지연이 **모든 쿼리의 첫 응답 앞**에 붙는다. 지연이 중요하면 `analyzer.prefer: "claude"`(외부 전송 가능한 요청만 해당)를 쓴다.
